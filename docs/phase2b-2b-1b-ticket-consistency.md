# Phase 2B-2B-1B チケット正本同期

`tickets[]`が唯一の正本。`ticketInfo`は常に先頭要素のコピーで、0件では`{ status: 'release_waiting' }`を表示専用の互換値とする。複数件は全件を保持するが、現在のフォームおよび両保存経路では保存を拒否する。

## 読み込みと編集

`normalizeRecordTickets`をlocalStorage・DB・seed・Excel取込・新規作成・インポート・保存境界に適用する。旧JSONで`tickets`がない場合だけ`ticketInfo`を移行する。発売待ちの初期値だけではチケットの存在を推定しない。それ以外の状態、ID、日付、枚数、購入先など具体的な情報があれば1件とする。正本配列があれば互換値より優先する。

配列型、要素、状態、UUID、枚数、フィールド型、ID重複を検証する。不正なlocalStorageは元の値を残し、自動永続化と追加・更新を停止する。200件未満や空配列も有効な保存データとして読み込む。キーの変更・削除・初期化は行わない。接続先DBのデータでローカル保存済みデータを上書きしない。

フォームの編集可能フィールドだけを既存の正本要素へマージする。ID、枚数、支払期限、購入先、チケット内の座席情報など未編集フィールドを保持する。新規要素のID未設定は許容する。既存レコードの`updatedAt`はフォームで変更しない。

Excelは明示的なチケット状態を優先する。状態も購入先もない行ではチケットを推定作成しない。購入先のみある旧Excel行は従来の観戦状態に基づく状態推定を維持する。

## 保存

RPCと旧RESTは、正本から導出した互換値を既存ペイロードへ変換する。RPCの既存フィールド・操作形式は変更しない。0件は`replace.ticket=false`とし、RESTもチケットを作らない。DBにチケットが残っているのに正本が0件の場合は、暗黙の削除や上書きをせず拒否する。既存UUIDの不一致やDB側の複数件も拒否する。

通常成功では両フィールドの整合性を維持してstateへ反映する。RPC成功後のDB `updated_at`を採用する。RESTも試合upsert応答のDB時刻を採用する。DB時刻をクライアント現在時刻で上書きしない。

RPC失敗・競合ではstateを成功値に変更しない。フォーム入力と元のDB時刻を保持し、失敗時の自動再取得でstateを置き換えない。旧RESTには従来から部分保存の可能性がある。

RPC成功後の時刻取得失敗は`refreshRequired`として区別する。保存済み内容はstateへ反映し、DB時刻は確認前の値を保持する。フォームは保存済み・再取得必要と通知し、入力を残して同フォームからの再送信を停止する。保存経路も対象IDの再保存を拒否する。正常な再読み込みで保存ガードを解除する。自動再保存・リトライはしない。

## ローカル検証と残課題

既存24テストを維持し、20テストを追加（合計44）。既存テストのチケット編集fixtureは正本を編集する形式に修正し、DB由来IDのfixtureはUUIDに変更した。Excel実ファイル形式のメモリ内取込、RPC・RESTモックで確認する。クラウドへの通信・書き込みは行わない。

Atomic Saveは既定のfalseを維持。Migration 0001〜0008は変更しない。複数チケット編集UI、Atomic Save有効化、クラウド統合検証は別工程。新規チケットにDBで採番されたUUIDの取得は次回のDB読み込みで行う（既存UUIDは編集・保存で保持）。
